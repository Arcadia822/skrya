# 每日输出模板反馈旅程

## 目标

让用户用自然语言调整每日简报的呈现方式，同时把可复用偏好沉淀成稳定规则，避免每次生成日报时重新解释一遍同样的审美和信息密度要求。

## 默认日报模板

日报默认使用纯 Markdown。原生飞书卡片由独立渲染器添加色块、徽标和列布局，不用字符框模拟卡片。

```markdown
# YYYY-MM-DD｜主题名｜每日简报

## 事件线时间线更新

### T-01 事件线名称
**最新进展**：
- [真实新闻标题](https://example.com/news) ｜ YYYY-MM-DD · N-01
事实简介及独立点评。

**历史时间线**：
- [已策展的重要节点](https://example.com/milestone) ｜ YYYY-MM-DD

## 今日简讯

### N-01 事件标题
事实简介。
为何重要：影响判断。
信源：[媒体](https://example.com/news)

---

## 可继续操作

- 回复 `dig: N-01`，展开新闻分析。
- 回复 `track: N-02`，建立追踪线。
- 回复 `dig: T-01`，查看全量历史。
- 回复 `write: T-01`，生成有来源的文章草稿，不自动发布。
- 自然语言反馈，调整后续偏好。
```

没有 active Thread 时省略事件线板块。存在 active Thread 但没有新增时，仍显示最新已知状态，不伪造新闻。底层全量历史保留，显示时间线只投影有明确 `milestone_reason`、真实日期与来源的关键节点。

## 反馈入口

用户不需要知道内部文件或配置字段。反馈分为以下入口：

1. 新闻分析，`dig: N-02` 或自然语言表达。
2. 建立追踪，`track: N-02`，先确认 seed 再持久化。
3. 全量历史分析，`dig: T-01`。
4. 文章草稿，`write: T-01`，不自动发布。
5. 自然语言偏好，区分内容范围、排序偏好和模板调整。

## 用户旅程

1. 用户收到包含 N-xx、T-xx、事实、信源和固定五项操作的日报。
2. 用户用自然语言指出一个具体问题，最好能带编号，但不能要求用户必须使用编号。
3. 系统先按被回复消息的已送达快照解析编号，再执行新闻分析、建线确认、全历史分析或文章草稿。偏好反馈进入对应配置确认，不改变旧卡片编号。
4. 对于会影响未来输出的反馈，系统先复述成稳定规则，例如“以后每条信源只显示最多两个来源，完整来源按需提供”。
5. 用户确认后，系统写入对应配置或模板约束；未确认时只把它当成本次聊天建议。
6. 下一次日报应用新规则，并在必要时用一句话提示“已按你之前的偏好压缩信源展示”。

## 模板偏好规则

模板反馈只应该改变呈现方式，不应该改变事件收集范围。典型映射如下：

- “信源太长”：保留单独的信源行，但限制展示数量，完整来源继续写入运行产物。
- “我想看影响”：在每条摘要里加入一句判断，不新增二级标题。
- “太啰嗦”：压缩每条摘要，不减少真实高价值事件。
- “别用英文来源名”：优先显示中文来源名；没有来源名时使用域名。
- “来源也要展示”：默认日报每条在空行后的信源行显示 compact source references。
- “中文表格线不齐”：使用纯 Markdown 或通道原生列布局，不使用 ASCII 行框或制表符。

## 成功标准

- 用户能在一次反馈内表达模板问题。
- 系统能区分“我要改日报长相”和“我要改关注范围”。
- 所有未来可复用的偏好都需要确认后再持久化。
- 大标题包含执行日期和主题。
- 简讯主体与固定操作区之间有 `---` 分隔。
- 操作区只包含五项解释清楚的后续操作，不夹带模型、版本、执行或投递结论。
- 日报使用统一编号的 Markdown 条目，原生卡片按已确认格式渲染，不为前几条另设样式。
- 信源默认可见，但不暴露 request id、内部文件名或抓取实现细节。
